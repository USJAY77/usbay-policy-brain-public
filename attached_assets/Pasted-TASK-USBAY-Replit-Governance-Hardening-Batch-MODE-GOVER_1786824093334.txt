1. GAP — HUMAN APPROVAL / IDENTITY REGISTRY
==================================================

RISK
A request could appear human-approved without cryptographically or structurally proving which authorized human granted authority.

REQUIRED MECHANISM
Implement or complete a bounded approval/identity registry for governed execution.

Requirements:

- Every privileged/high-risk governed execution must bind:
  actor_id
  actor_type
  authority_scope
  approval_id
  execution_contract_id
  policy/decision reference
  issued_at
  expires_at where applicable
  integrity reference/hash

- Unknown actor -> DENY
- Missing approval -> DENY
- Invalid approval -> DENY
- Expired approval -> DENY
- Approval for another contract -> DENY
- Approval replay outside permitted scope -> DENY
- Actor/approval substitution -> DENY

Human approval must never be inferred from:
- UI state
- session presence
- an unchecked boolean
- model output
- provider response
- caller-supplied unverified metadata

No autonomous approval creation.

TEST FIRST:
Create failing tests proving execution currently cannot establish the required binding where applicable, then implement the minimum control.

==================================================
2. GAP — SUBPROCESS SECRET ISOLATION + EXECUTION BOUNDS
==================================================

RISK
Spawned commands may inherit excessive environment secrets or execute indefinitely.

REQUIRED MECHANISM

For subprocess execution:

- construct an explicit allowlisted environment;
- do NOT pass the complete parent environment by default;
- deny secrets not explicitly required for that execution contract;
- never log raw secret values;
- set explicit timeout/deadline;
- terminate timed-out child processes;
- clean up child processes;
- capture bounded stdout/stderr safely;
- cap excessive output where appropriate;
- surface deterministic fail-closed error states;
- record governed audit evidence.

Tests must prove:

A. unapproved secret is NOT visible to child process;
B. approved minimal variable can be passed when explicitly authorized;
C. command timeout terminates the process;
D. timeout cannot be interpreted as successful execution;
E. child-process failure produces evidence;
F. no raw secret appears in logs/evidence/client response.

Do not break the existing valid subprocess path.

4. GAP — PROVIDER RESULT / EXTERNAL RESULT INTEGRITY
==================================================

RISK
An external provider response could be substituted, malformed, replayed, or accepted without binding it to the governed request.

Inspect the current provider-result path.

Where the mechanism is missing, implement the minimum bounded validation layer that binds accepted results to:

- provider identifier
- governed request/execution id
- execution contract id where applicable
- response/result hash
- timestamp/freshness data where available
- expected result type/schema
- policy/evidence reference

Required failures:

- missing required provenance -> DENY / reject
- malformed result -> reject
- mismatched request/execution id -> reject
- unsupported provider -> reject
- stale/replayed result where freshness is required -> reject
- unvalidated result must never become authoritative evidence

Do NOT claim cryptographic provider authenticity unless a real provider signing mechanism is actually present and verified.

If cryptographic authenticity is unavailable:
evidence state = PARTIAL, not PROVEN.
