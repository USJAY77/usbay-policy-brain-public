# USBAY governance dashboard

## "Euria" branding does not exist — product is USBAY
Users repeatedly ask to verify/render "Euria" fields (e.g. `authority_euria`, "Euria Analysis ID"). The codebase has zero "Euria" references; everything is USBAY-namespaced. When a request names "Euria", confirm whether they want a net-new feature vs. the wrong project — do NOT assume an "API mapping bug."
**Why:** Avoids building on a false premise. A user did confirm they wanted "Euria" built as a brand-new preview-only UI layer on top of USBAY.

## Preview-only demo sections: two homes, two %-rules
Two distinct injection sites for preview-only UI. Both are client-side only (no fetch/backend), self-contained (scoped CSS prefix + IIFE), and must NOT touch governance logic.
1. **`_simulator_block_html()`** (grep that def) — injected at top of `<main>` on BOTH `/` and `/playground`. It returns a PLAIN triple-quoted string with NO Python `%`-formatting → use SINGLE `%` in CSS (do NOT write `%%`). The intake modal ("Start Governance Assessment" → "Generate preview" submit id=`usbsim-intake-submit`, handler `generatePreview()`) lives here.
2. **`playground_html()`** page builder — runs through Python `%`-formatting → escape every literal `%` as `%%`. Playground-only sections (e.g. demo-readiness) go here, before the runtime-telemetry `strip`.
Always `esc()`/`garEsc()` all dynamic JS values regardless of site.

## Governance Assessment Result is wired to "Generate preview", not a standalone button
The Governance Assessment Result panel (id=`usbsim-gar`) is rendered by `generatePreview()` inside the intake preview output (`#usbsim-intake-out`, itself inside the intake modal). Because it lives in `_simulator_block_html()`, it shows on both `/` and `/playground`. A prior standalone `#usbsim-assess` section (playground-only, own "Start Governance Assessment" run button) was removed to avoid a duplicate panel.
**Why:** user reported the panel "did not render" because they were on `/` where only the simulator block exists; the standalone panel was playground-only. Consolidating into the Generate-preview flow fixes both pages with one source of truth.
**How to apply:** outcome model lives in `GAR_DATA` (ALLOW/BLOCKED/HUMAN_REVIEW/FAIL_CLOSED → rec/sig/ts/euria/usbay/human); toggle chips re-render; IDs are random hex (`garHex`), illustrative only.

## Test runner quirk
Repo has ~150 test files (~1641 collected tests); whole-repo `pytest` exits `-1`/hangs in the sandbox — run per-file/per-target or per-marker (`-m critical`, `-m governance`). No `pytest-xdist` (`-n` unsupported). Some files hang on missing services (`test_redis_store`, `test_hydra_consensus`) — run lighter files individually with `timeout`. Gateway-relevant suites: `tests/test_gateway_app.py` (37 tests, all pass), `tests/test_governance_dashboard.py`. `./signed_test.py` is a live-network test that fails on SSL verification offline — pre-existing, unrelated.

## Pre-existing openssl Ed25519 test failures (sandbox env, NOT your change)
In the sandbox, the `critical` + `governance` lanes have ~5 pre-existing failures rooted in openssl Ed25519 signing/verification: `pkeyutl: Option unknown option -rawin` and `SystemExit: EVIDENCE_ED25519_SIGN_FAILED`. Affected: `tests/test_governance_validation.py` (committed-policy signature verify / fail-closed-on-changed-policy), `tests/test_production_readiness.py` (CI evidence manifest signature tests). Source: `runtime/policy_validator.py:~222`, `scripts/generate_ci_evidence_manifest.py:~824`.
**Why:** the sandbox openssl build lacks `-rawin` (raw Ed25519). These are environment-blocked, unrelated to any UI/simulator change — do NOT try to "fix" them when verifying a frontend task.

## Dev-preview 502 — root cause + fix
Bare dev domain returned 502 while `:5000` was 200, because `.replit` `[[ports]]` pins externalPort 80 -> localPort 8765 (stale; nothing listens there) while the app runs on 5000. `.replit` cannot be edited directly (platform-protected) and `configureWorkflow` only sets the workflow's own `waitForPort` (5000) — it does NOT reassign the stale externalPort, and a hard restart does not reconcile a pinned `[[ports]]` entry.
**Fix:** added `scripts/preview_port_forward.py` (stdlib asyncio TCP relay 0.0.0.0:8765 -> 127.0.0.1:5000) and run it backgrounded in the workflow command before uvicorn. This makes externalPort 80 reach the app, so bare `/` and `/playground` return 200. Production unaffected (uses `$PORT`).
**Why a relay, not a .replit edit:** direct `.replit` edits are blocked and no exposed tool rewrites externalPort; the relay is the minimal, reversible, governance-logic-free way to satisfy the existing 80->8765 mapping. The workspace preview pane / screenshot tooling also expect the app on port 80, so this fixes those too.

## Wizard checklist "bags" must be cleared in place, never reassigned
The Governance Pilot Wizard stores per-item toggle state in shared objects (`wizChecks.milestones/evidence/approvals/criteria`). `wizBindChecks()` adds ONE delegated `change` listener per container that closes over the bag object reference. Render/read (`wizRenderChecks`, `wizSelected`) read from `wizChecks.<bag>`.
**Why:** Reassigning a bag (`wizChecks.evidence = {}`) on restart / intake-handoff orphans the listener — it keeps writing to the old object while renders read the new one, so toggles silently stop persisting. Fix is `wizResetChecks()` → `wizClearBag()` which `delete`s keys in place, preserving object identity.
**How to apply:** any new wizard checklist must (1) bind once via `wizBindChecks`, (2) reset only by clearing in place. Adding a new bag means adding it to `wizResetChecks()` AND to the `wizBindChecks` calls at init.

## Governance Pilot Wizard is 9 steps and bridges from the assessment
Flow: assessment modal ("Generate preview") shows recommended license → "Continue to Governance Pilot" button (`#usbwiz-from-intake`) copies assessment form fields into `#usbwiz-form`, closes intake, and `openWiz(3)` jumps to Scope. Wizard steps: 1 Assessment, 2 License, 3 Scope, 4 Objectives, 5 Evidence, 6 Approvals, 7 Criteria, 8 Timeline, 9 Summary. CTA label is gated on `WIZ_MAX-1`/`WIZ_MAX`, not hardcoded step numbers.
**Why:** user wants the license recommendation kept as the bridge between assessment and pilot (no payment/booking framing). Assessment and wizard share identical form field `name`s, so prefill is a plain value/checkbox copy.

## Recommended Pilot Engagement section (assessment result) — capture + summary
A second capture+generate block lives after the Recommended License card (`#usbsim-pileng`, form `#usbeng-form`: company/industry/country/challenge/aisystems/regulatory; button `#usbeng-generate`; output `#usbeng-summary`). It follows the GAR pattern of a self-contained inline `<style>` with scoped `usbeng-*` classes. `prefillEngagement(industry, usage, opts)` is called in `generatePreview` right after `applyLicensingFromAssessment` and overwrites the 3 derived fields (industry/aisystems/regulatory via INDUSTRY_LABELS/USAGE_LABELS/REG_LABELS) + hides the stale summary; company/country/challenge are never auto-filled. `generateIntakeSummary()` builds the summary via innerHTML but escapes every dynamic value with a local `esc()` helper, and reads the recommended license + posture from existing `#intake-lic-*`/`#intake-dim-*` textContent (illustrative, like buildDemoSummary).
**Why:** UI-only demo — no payment, no account, no governance-logic change; summary is a client-side illustrative artifact.
**How to apply:** any new field added to the summary HTML MUST go through `esc()`. USAGE_LABELS/REG_LABELS were added near the intake license vars (no equivalent existed before).

## Executive Governance Report ↔ wizard share state via an outer-scope `wizApi`, not DOM-scraping
The single Executive Report modal (`#usbsim-rpt`, opened by `#usbsim-rpt-open`) and `buildReport()` live in the OUTER simulator IIFE scope; the wizard's compute helpers (`wizCollect`/`wizSelected`/`wizChecks`/`wiz*Defaults`/`wizScopeText`/`wizAiSystems`/`wizTimeline`/`wizLicKey`) are defined inside the INNER `if (wiz) {…}` block and are NOT reachable from the outer scope. Pattern: declare `var wizApi = null;` in the outer scope and assign it (object of those helper refs) inside `if (wiz)` just before `wizShow()`. `buildReport()` then computes EVERYTHING from one `s = wizApi.collect()` snapshot (license/maturity%/risk/scope/objectives/evidence/approvals/criteria/timeline), giving a true single source of truth that matches the wizard plan. Engagement-only fields (company/country/challenge/regulatory/aisystems) are read from `#usbeng-form`; gaps are recomputed locally via `reportGaps(s)` mirroring the assessment axis logic (MAT/REV/AUD/ENF_LABELS, top-3 lowest value/max). Guard every wizApi use with `if (s)`/null fallbacks since wizApi is null until the wizard block initializes.
**Why:** reading rendered wizard DOM is fragile (only populated for visited steps); the shared-helpers approach keeps the report consistent with the wizard regardless of navigation and avoids duplicating governance logic.
**How to apply:** DOM is always readable cross-scope, but inner FUNCTIONS are not — expose them via an outer var. Escape all dynamic values: scalars via `textContent` (`setT`), list/kv innerHTML via local `esc()`. Report sections use `usbsim-rpt-*` classes; current ids are `rpt-exec-*`/`rpt-challenge-*`/`rpt-lic-*`/`rpt-risk-*`/`rpt-gaps`/`rpt-scope-kv`/`rpt-objectives`/`rpt-approvals`/`rpt-evidence`/`rpt-criteria`/`rpt-timeline`/`rpt-next-*`.

## Executive Report is EXACTLY 12 numbered sections — user-confirmed order (kept Risk Summary AND Gaps)
The board report's canonical, user-confirmed section order is: 1 Executive summary, 2 Governance challenge, 3 Recommended license, 4 Governance risk summary, 5 Governance gaps, 6 Pilot scope, 7 Governance objectives, 8 Human oversight requirements, 9 Evidence requirements, 10 Success criteria, 11 Pilot timeline, 12 Recommended next step. A non-numbered "For your board" audience block stays at the top, unnumbered. "Governance objectives" (#rpt-objectives) renders the wizard milestones: `setList('#rpt-objectives', s ? wizApi.selected(wizApi.milestoneDefaults(s), wizApi.checks.milestones) : null)` — same source as the wizard plan's "Governance objectives" block.
**Why:** the report briefly went to a 10-section variant (Exec Summary + Gaps dropped), then the user reverted to the full 12 sections, KEEPING Executive Summary, Governance Gaps, AND Governance risk summary. Both `reportGaps(s)` and the `rpt-exec-*`/`rpt-gaps` ids are live again — do not remove them without an explicit request. Single source of truth chain: Assessment → License → Pilot Wizard → Executive Governance Report.
**How to apply:** when editing report sections keep heading numeric prefixes (`N · …` in HTML body) AND the `// N · …` build comments in `buildReport()` in lockstep 1..12. No PDF/export/download — preview-only modal by design.

## "Copy Executive Report" button reads rendered DOM, not the snapshot
Footer button `#usbsim-rpt-copy` (in `.usbsim-rpt-footbtns` next to Close) copies a plain-text recap via `buildReportText()`, which walks the RENDERED report DOM (`.usbsim-rpt-body > .usbsim-rpt-sec`: `.usbsim-rpt-sec-h` headings, `p.usbsim-rpt-v`, `ul.usbsim-rpt-list>li`, and kv lists `.usbsim-rpt-kvk/.kvv` + audience `.usbsim-rpt-audk/.audv`). Uses `navigator.clipboard.writeText` with a hidden-`<textarea>` + `document.execCommand('copy')` fallback; `flashRptCopy(ok)` shows transient confirm/fail text (`.usbsim-rpt-copy-ok` green class) and reverts after ~1.8s.
**Why:** copying from the live DOM guarantees the text matches exactly what is on screen (consistent with the single-source-of-truth principle) and survives section re-specs without separate maintenance.
**How to apply:** if you add a new section markup pattern/class to the report, extend `buildReportText()`'s selectors or it will be silently omitted from the copy.

## Governance approval is a SEPARATE Pilot Request intake modal, NOT a wizard step
Governance approval was moved OUT of the wizard (wizard is back to 9 steps; all `wizApproval*`/`WIZ_APPR`/`usbwiz-appr-*`/step-10 code deleted). It now lives in a dedicated **Pilot Request → Governance Approval** modal (`#usbpr`, body `#usbpr-body`) opened by a "Submit Pilot Request →" button (`#usbsim-rpt-pilot`) in the Executive Report footer (Copy/Close demoted to ghost). Clicking it does `closeRpt(); openPr()`. The modal reuses the `.usbsim-rpt-*` shell + repurposed `.usbpr-*` CSS (renamed from the old `usbwiz-appr-*`). All `pr*` JS lives in the OUTER simulator IIFE scope (alongside `buildReport`/`wizApi`), state in `var prReq = {name,org,role,id,ts,status,submitted,history}`; statuses in `PR_APPR` map.
**Requester identity (fail-closed):** the DRAFT modal shows a requester form (Name, Organization [prefilled from `#usbeng-form` company, never asked twice], Role) — `prAction('submit')` requires ALL THREE non-empty or it blocks with `#usbpr-err` + focus. A pilot CANNOT be submitted without a named accountable requester. After submit the form seals into a read-only KV. Requester identity appears in the Pilot Request modal, the approval review body, AND the Executive Report exec KV (`buildReport` pushes Accountable requester/Requester role/Requester organization/Pilot Request id+status onto `execKv` when `prReq.submitted`).
**State machine:** DRAFT → SUBMITTED → PENDING_GOVERNANCE_REVIEW → {APPROVED | HUMAN_REVIEW_REQUIRED} → PILOT_ACCEPTED, with REJECTED/reset branches. PILOT_ACCEPTED is reachable ONLY via an explicit human "Accept Pilot (human approver)" action from APPROVED/HUMAN_REVIEW_REQUIRED — never directly from governance "approve". Buttons are gated by status in `prButtons()`. Everything else (license/risk/evidence/approvals/timeline/challenge/risk drivers) derives from `wizApi.collect()` — same single-source chain as the report.
**Why:** user asked to convert the pilot flow into a governed intake process where approval is a post-report request step with captured accountable-requester identity (preview-only; USBAY=ENFORCEMENT_AUTHORITY, Euria=ANALYSIS_ONLY label only, human approval MANDATORY, fail-closed DEFAULT). Nothing stored/transmitted — all client-side.
**How to apply:** `wizApi` now also exposes `challengeText` + `riskDrivers` (added so the PR modal can reproduce report content without DOM-scraping). Escape all dynamic values via `prEsc`. Guard `wizApi` use with `if (s)` since it's null until the wizard block inits.

## Pilot intake is a multi-request QUEUE — `prReq` is one record, `prQueue[]` holds many
The single-record model was upgraded to a session queue (user wants reviewers to work through several pilot requests). `prReq` is no longer a singleton literal: it's `prNewDraft()` (adds a `snap:null` field) and there's an outer-scope `var prQueue=[]`. On submit, `prReq.snap=prSnapshot(org)` captures license/risk/industry/company/country/regulatory/aiSystems/challenge/riskDrivers/evidence/approvals/timeline AT submit time, then `prQueue.push(prReq)`. `prReset()` (the "Start a new pilot request" action) now does `prReq=prNewDraft()` so the old record STAYS in the queue. `prRender()` reads from `prReq.snap` when `submitted` (sealed), else live `prSnapshot(prReq.org)` for the draft preview.
**Queue modal** `#usbpq` (reviewer view, opened by `#usbsim-rpt-queue` ghost btn in report footer AND by the `data-pr="queue"` "View in Intake Queue →" btn appended in `prButtons()` for every submitted/terminal state). `pqRender()` shows stats (`pqStat()`) + a `.usbpq-table` of all queued requests (ID/Requester/Org/Role/License/Risk/Submitted/Status badge + a `data-pq="<idx>"` Review btn). Clicking Review → `closePq(); openPrRecord(prQueue[idx])` which sets `prReq=rec; openPr()`.
**Shared-reference is intentional:** `prQueue.push(prReq)` stores the same object identity, so reviewer status/history mutations on the opened record reflect in the queue. Reset rebinds `prReq` to a fresh object, leaving queued records intact — no corruption path. Status badges reuse `.usbpr-status s-*` via `PR_APPR[r.status].cls`.
**Why:** preview-only governance simulation demonstrating intake/prioritization/review/approval across multiple requests; session-only memory (no storage/persistence/transmission). Architect review PASSED (no blocking issues).
**How to apply:** all queue values escaped via `prEsc`; the `<idx>` in `data-pq` is internally generated. CSS is `.usbpq-*` (added before the 640px media query) + `.usbpr-act.act-queue`.

**Queue triad — filter bar + legend + per-status breakdown:** `PQ_META` (7 entries `{k,short,legend}`, defined order DRAFT→SUBMITTED→PENDING_GOVERNANCE_REVIEW→HUMAN_REVIEW_REQUIRED→APPROVED→REJECTED→PILOT_ACCEPTED) is the SINGLE source for all three; reuse it, don't re-list statuses. `pqStat()` returns a per-status count map (replaced the old grouped {total,pending,...}). `pqRender()` emits: summary chips (total + one count per status, color via `pqCls(k)`=`PR_APPR[k].cls`), a `.usbpq-filters` bar (`data-pqf="ALL"|<status>` buttons, `is-active` on `pqFilter`), the table, then a `.usbpq-legend`. `var pqFilter='ALL'` (outer scope); `openPq()` resets it to ALL. The pqBody click listener resolves `[data-pqf]` FIRST (set pqFilter + re-render + return) BEFORE `[data-pq]` Review. **Index integrity:** filtered rows still use the TRUE `prQueue` index for `data-pq` (loop over full queue, `continue` on non-match) so Review opens the right record. Empty-queue → `.usbpq-empty`; filtered-to-nothing → `.usbpq-nomatch`. **DRAFT chip/count is intentionally always 0** (drafts never enter prQueue) — user explicitly wanted all 7 shown for completeness. Architect review PASSED.

**Queue is now PRE-SEEDED for demos:** `prQueue` init was changed from `[]` to `prSeedQueue()` — 5 sample records (one each: PENDING_GOVERNANCE_REVIEW / HUMAN_REVIEW_REQUIRED / APPROVED / REJECTED / PILOT_ACCEPTED), each a complete record (`name/org/role/id/ts/status/submitted:true/history[]/snap{}`) so the Review modal renders fully. The live Submit-Pilot-Request flow still `prQueue.push(prReq)`, so a new submission appends as the 6th row. DRAFT/SUBMITTED counts stay 0 (terminal/in-review statuses only). Seed records are static literals — no `wizApi`/`prSnapshot` dependency.
**Evidence-screenshot quirk:** the `.usbpq-table` overflows the modal card (last cols Recommended License/Risk/Status/Review get clipped under `.usbpq-tablewrap{overflow:auto}`). To capture all 8 columns in a Playwright shot, inject evidence-only CSS (`page.add_style_tag`) widening `#usbpq .usbsim-rpt-card` + `overflow:visible` on the wrap — DOM-side only, never an app code change.

## Playwright evidence in THIS sandbox — three hard-won execution rules
The chromium env is memory/cgroup-fragile. What actually works (CHROME path + no-sandbox/disable-dev-shm/disable-gpu as before):
1. **Run FOREGROUND in a single bash tool call** (`timeout 100 python3 -u <script>`). Background/`nohup &` processes are KILLED when the bash tool call ends (the `&` child shares the tool's process group) → log file vanishes, 0 output.
2. **Do NOT put `pkill -f chromium` in the SAME command that launches chromium** — it reliably OOM-kills the bash shell (exit 137). If you must clean strays, do it in a SEPARATE prior tool call, then verify `ps | grep chrom == 0`, then launch in a clean call with NO pkill.
3. **Avoid `--single-process`** foreground (OOM-kills the shell, 137) and avoid `device_scale_factor=2` + tall viewport (memory spike). Use multi-process, `device_scale_factor=1`, viewport ~1240×1320. For element captures disable transitions (`page.add_style_tag("*{transition:none!important;animation:none!important}")`) + `el.screenshot(animations="disabled")` to dodge "element is not stable".
Scripts: `scripts/_evidence_lifecycle.py` (9 stage PNGs), `scripts/_compose_lifecycle.py` (3×3 montage → `evidence/lifecycle_journey_full.png`). **Pillow montage glyph trap:** source strings use literal `\u2014`/`\u2192`/`\u2022` escapes (the file is ASCII text); the default font renders these as tofu boxes — replace the ESCAPE-SEQUENCE text (`sed 's/\\u2014/-/g'`), not the unicode char, or use ASCII (`-`,`->`,`|`).

## Element-screenshot of a TALL section bleeds the relative `.topbar` into the capture
When Playwright `element.screenshot()` / `el.screenshot()` captures a section taller than the viewport (captureBeyondViewport stitching), the page's `.topbar` header (and `body::before` fixed bg) bleed into the stitched image and OVERLAP the captured element's top — even though `.topbar` is `position:relative` and sits ABOVE `<main>` in the DOM. Symptom: the section's own top content (e.g. the evidence cover's board title + decision stamp) is hidden behind the app nav/runtime-strip.
**Fix:** before capture, inject evidence-only CSS `page.add_style_tag(content=".topbar{display:none !important;} body::before{display:none !important;}")` (DOM-side only, never an app code change). This is in addition to the transition/animation disable rule.
**Why:** purely a capture artifact of full-element stitching, not a layout bug — hiding the app chrome for the shot is the minimal, non-invasive fix.
