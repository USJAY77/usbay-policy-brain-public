# Non-PB CI maintenance review-body route

Route: `non_pb_ci_maintenance.v1`. This is a narrow review-text route,
not a dependency-risk downgrade, approval exception or merge authorization.
It becomes applicable only after this rule clarification has undergone the
required human reviews/checks and has been adopted into the governing baseline.
Passing local tests does not adopt the route or modify an existing PR.

## Eligibility and evidence

Use only for dependency provisioning and CI configuration corrections whose
full patch does not change policy semantics, authorization, tenant isolation,
replay, audit behavior or execution authority. Required reviewers remain
USBAY-GLOBAL23 and USBAY-AUDIT. Dependency governance policy, branch protection
and all applicable required checks/evidence remain unchanged, including higher
risk requirements for cryptographic/verifier-adjacent dependencies.

Machine checks permit only added/modified `.github/workflows/<safe-name>.yml`
or `.yaml` and root `requirements-<safe-name>.txt` paths. Deletions, renames,
unknown types, duplicate paths, empty/mixed changesets and protected-source
paths require PB routing or human clarification. Workflow/dependency edits can
still alter protected behavior: humans must review the actual diff, dependency
impacts and referenced evidence. A path match or owner classification alone
does not prove unchanged semantics, authority or approval.

The CLI reads the complete committed diff between exact base and candidate
SHAs through Git. It does not inspect ignored/untracked changes as part of that
commit, and does not attest the working tree. Direct API callers must supply
the complete observed changeset; caller-supplied inventories or references are
not authenticated attestations. Git reads have a 10-second timeout and a
post-capture 64k text check, not a hard intermediate-memory bound.

## Contract

Closed metadata fields: `route`, `repository`, `base_sha`, `candidate_sha`,
`classification_reference`, `purpose`, `risk`, `policy_reference`,
`validation_reference`, `validation_head_sha`, `validation_summary`, `audit`,
`impact`, `rollback_plan`. All are exact nonempty strings; SHA fields are
40 lowercase hexadecimal characters. The evidence SHA must equal candidate.
The Actions URL must be in the declared repository. References identify
supplied records, not verified identity/signatures or automatically trusted CI.
No PB number, approver identity enrollment, signature or approval field exists.
No human authority is created. Text budgets and heading injection checks apply.

`generate_body` and `validate_body` reuse the existing required-section validators.
Validation requires exact regenerated bytes, preserving required reviewers,
REVIEW_REQUIRED/AWAITING_APPROVAL, evidence and changeset. All required purpose,
risk, policy, checks, audit, impact, validation/source and rollback sections are
populated; no legacy placeholders. No publication, tests or application calls
are triggered by generation. CLI prints to stdout only.

Example invocation after adoption (metadata file must already exist):
`python -m scripts.non_pb_ci_maintenance_body --metadata-json candidate.json --repo-root .`

## PB compatibility and adoption

Existing PB-023/025/026 generators and PB title/commit validation are unchanged.
Mixed/ambiguous scope cannot bypass them using this route. This clarification
itself changes body-governance rules and is not eligible as non-PB CI maintenance;
its adoption must use the existing governance review route or applicable human
clarification. The proposed body for #397 is prospective until adoption.
